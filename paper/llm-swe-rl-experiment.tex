\begin{abstract}
We ask whether a reinforcement-learning-from-verifiable-rewards loop for single-function software repair can complete on one recorded 8~GB consumer GPU. We train a rank-16 LoRA adapter on the 0.49B-parameter Qwen2.5-Coder model for \TrainSteps{} Group Relative Policy Optimization steps. Four candidate repairs per prompt receive one composite reward: structural rejects are handled on the host, deterministic cache hits reuse an earlier breakdown, and valid cache misses run hidden unit tests in fresh resource-limited Docker containers. Training completed in \TrainSeconds{} seconds with \TrainPeakGiB{}~GiB peak allocated GPU memory and changed all \ChangedTensors{} trainable adapter tensors. Validation improved from \BaseValSolved{} to \ModelValSolved{} greedily solved tasks and selected the 100-step checkpoint. On the 12-task internal set held out from model optimization and selection, full greedy solves rose from \BaseTestSolved{} to \ModelTestSolved{}, but mean greedy hidden-test correctness changed from \BaseTestHidden{} to \ModelTestHidden{} (paired difference \TestDifference{}, paired percentile-bootstrap 95\% interval \TestInterval{}). On frozen HumanEvalFixDocs-Python, greedy pass@1 changed from \BaseExternalPassed{} to \ModelExternalPassed{} (difference \ExternalDifference{}, paired percentile-bootstrap 95\% interval \ExternalInterval{}). Invalid internal candidates were \BaseInvalid{} versus \ModelInvalid{}. The result establishes an end-to-end, publicly reloadable RL pipeline and an observed output-validity difference; it does not establish a statistically conclusive general repair-capability gain.
\end{abstract}

\section{Research question and contribution}

Software is unusually suitable for verifiable reinforcement learning because candidate behavior can be checked by executable tests rather than a learned preference model. The practical obstacle is that serious repository-scale agent benchmarks often combine large policies, long contexts, tool orchestration, and substantial compute. This experiment narrows the domain to deterministic single-function Python repair and asks:

\begin{quote}
Can a sub-billion-parameter code model receive genuine group-relative policy updates from hidden tests, on one 8~GB GPU, while retaining explicit split discipline, resource-limited execution isolation, auditable evidence, and a resulting model that another user can load?
\end{quote}

The gate pre-specified in producing source commit \texttt{\SourceCommit} was that 100 low-rank GRPO steps would improve validation hidden-test correctness by at least 0.05 or solve one additional validation task, without worsening the aggregate format/runtime/policy status rate \cite{sourcecommit}. The experiment contributes (i) a version-pinned implementation; (ii) a project-authored 36/12/12 train/validation/test curriculum with structural leakage checks; (iii) a Docker-mediated reward path; (iv) selection-locked internal and external paired evaluation; and (v) public merged and adapter artifacts. Project authorship is a repository declaration, not an independent originality audit.

The scope is intentionally modest. A function-repair policy is not a repository agent, and passing small unit-test suites is not evidence of broad software-engineering autonomy.

\section{Foundations and implementation choice}

GRPO was introduced as a policy-optimization variant that forms relative advantages from groups of sampled completions while avoiding a learned value model \cite{deepseekmath}. TRL exposes the algorithm, custom reward functions, PEFT integration, and DR-GRPO loss in a maintained trainer interface \cite{trl}. LoRA represents the update with small trainable low-rank matrices while leaving base weights frozen \cite{lora,peft}. These properties make the combination suitable for limited memory.

Qwen2.5-Coder provides instruction-tuned code models down to a reported 0.49B parameters \cite{qwen,qwenmodel}. The pinned base is
\begin{center}
\small\texttt{Qwen/Qwen2.5-Coder-0.5B-Instruct}\\
\texttt{commit \BaseRevision}.
\end{center}
The pinned public DebugArena model card motivated the particular 0.5B model, four-completion group, and $10^{-5}$ learning rate \cite{debugarena}. Its illustrative snippet does not define its reward function, dataset construction, adapter attachment, isolation, held-out protocol, or a released trained checkpoint. MiniBug-RL therefore uses the installed, version-pinned TRL, PEFT, Transformers, and Hub APIs rather than treating that snippet as a complete recipe.

\section{Method}

\subsection{Curriculum and prompt contract}

The project-authored curriculum contains 60 short, import-free functions: 36 training, 12 validation, and 12 final-test tasks. Families include incorrect comparisons, boundary and off-by-one errors, bad state updates, accumulation errors, indexing mistakes, and Boolean logic. Each task has a natural-language specification, buggy source, two public JSON examples, and no gold repair; 59 tasks have four hidden JSON cases and one has five \cite{runsummary}.

The model receives only the specification, buggy function, and public examples. It is instructed to return exactly one complete replacement function. A versioned manifest hashes canonical task records and normalized abstract syntax trees. Bound names are alpha-normalized and literal values are masked by type before structural hashing; no normalized template crosses a split. Every original bug was run in the real container and shown to fail at least one hidden case before training \cite{sourcecommit,runsummary}.

\subsection{Reward and isolation}

For a valid candidate with $n$ hidden tests, let $p$ be the fraction passed and $I$ indicate a full solve. The ordinary successful-execution reward is
\begin{equation}
  r = p + I[p=1] + 0.1,
\end{equation}
so a syntactically valid but wholly wrong function earns 0.1 and a complete repair earns 2.1. Invalid structure returns $-0.3$, a prohibited construct returns $-1.0$, and a valid function that crashes or times out receives $0.1-0.25=-0.15$. Expected values remain in the trusted host process; only candidate source and JSON call inputs cross the container boundary. Actual results return to the host for comparison \cite{sourcecommit}.

Across the two-step smoke and 100-step main training, the 404 rollout records comprised 38 host-side structural rejections, 175 deterministic cache hits, and 191 valid cache misses. Each valid cache miss ran in a newly named container from this immutable image ID \cite{runsummary}:
\begin{center}
\small\texttt{sha256:\DockerImageDigest}.
\end{center}
Networking is disabled (\texttt{--network none}) and the root filesystem is read only. The runtime drops all capabilities, sets \texttt{no-new-privileges}, uses non-root UID/GID 65532, and supplies no host bind mount, named volume, Docker socket, secret, or GPU device. Its only explicit mount is a 16~MiB \texttt{/tmp} tmpfs with \texttt{noexec,nosuid}. It also sets a 32-PID limit, 128~MiB memory with no swap, a 0.5-CPU scheduling quota, and a separate host-enforced wall-clock deadline. The pinned Docker 29.4.1 CLI reference documents these run flags \cite{dockerrun}. AST filtering and reduced builtins are defense in depth, not a security boundary.

\subsection{Model update}

The implementation uses BF16 Transformers/PEFT rather than 4-bit loading. LoRA rank is 16, alpha is 32, dropout is zero, bias is disabled, and \texttt{all-linear} targets linear and Conv1D layers except the output layer. This produces \TrainableParameters{} trainable parameters (\TrainablePercent{} of 502,830,976 total).

The main GRPO configuration is shown in Table~\ref{tab:training}. The effective optimizer batch is $1\times4=4$, divisible by the four generations. Reward scaling is disabled, $\beta=0$ omits a reference-model KL term, the DR-GRPO loss uses the fixed completion-length divisor, and fully truncated completions are masked. Gradient checkpointing and SDPA reduce memory. A callback would stop if more than 80\% of groups had zero reward variance for 20 consecutive logs \cite{trl,sourcecommit,runsummary}.

\subsection{Source-committed selection and evaluation}

The untouched base, two-step smoke adapter, and 100-step adapter use identical validation prompts, task-level seeds, decoding, and sandbox. Candidate adapters are ranked lexicographically by mean greedy hidden-test fraction and then greedy full-solve rate. The learning gate requires a hidden-fraction point gain of at least 0.05 or one additional solved task, and an aggregate rate of invalid, timeout, runtime, and policy statuses no worse than the base.

The optional 200-step continuation decision was made before any final model generation, score, or outcome was available. Internal final task definitions and hidden cases had already been loaded and structurally checked; HumanEvalPack rows were loaded only in the subsequent evaluation path. The 100-step adapter passed the gate, while mean training rewards in steps 51--75 and 76--100 were 1.5230 and 1.5355. The checkpoint was locked rather than extending the budget opportunistically \cite{runsummary}.

Internal evaluation uses one greedy and four sampled candidates per task. ``Observed sampled success@4'' is the fraction with at least one full solve among exactly four recorded draws, not the unbiased pass@$k$ estimator discussed by Chen et al. \cite{codexeval}. Reported intervals use 10,000 paired task-level percentile-bootstrap resamples with seed 42.

Only after selection, the same checkpoint is evaluated on HumanEvalFixDocs-Python from HumanEvalPack \cite{octopack,datasetcard}, pinned to dataset revision
\begin{center}
\small\texttt{9a41762f73a8cb23bb5811b73d5aab164efcf378}.
\end{center}
There is one greedy candidate for each of 164 tasks. The prompt conversion and first-block stopping follow the pinned BigCode harness \cite{bigcodeharness}. MiniBug-RL applies a three-second wall-clock deadline to its resource-limited container, stricter than the harness's 10-second Python limit; the score is therefore not leaderboard-identical.

\section{Results}

\subsection{Training viability}

The two-step smoke changed 168 adapter tensors and survived save/reload. Main training reached exactly \TrainSteps{} steps with finite loss \TrainLoss{}, changed all \ChangedTensors{} trainable tensors, and had adapter $\ell_2$ delta \AdapterDelta{}. Peak allocated GPU memory was \TrainPeakBytes{} bytes (\TrainPeakGiB{}~GiB), below the recorded 8,151~MiB device capacity. The longest zero-reward-variance streak was eight, below the 20-log stop threshold. Four of 400 main-training rollouts were clipped at the completion limit, all by step 31. The structured log records no training, CUDA, or reward-collapse failure; process stderr was not part of that log, so it cannot certify every third-party diagnostic stream \cite{runsummary}.

Validation selected the main adapter with a greedy hidden-fraction difference of \ValDifference{} (paired percentile-bootstrap 95\% interval \ValInterval{}) and one additional solved task. Thus the precise structural result is fewer invalid candidates, not an improvement in every failure category \cite{hubresults,taskscores}.

\section{Error analysis and interpretation}

The largest observed behavioral difference is format adherence on the internal final protocol: invalid candidates were 19 for base and one for the selected adapter among 60 greedy-plus-sampled candidates per system. This matters operationally because prose, multiple functions, and malformed source receive host-side penalties without reaching hidden-test execution. The single run does not isolate why sampled partial correctness also differed.

Correctness changes were heterogeneous. Relative to base, greedy internal improvements occurred on Boolean parsing, nearest multiples, wrapped indexing, and pair sums; regressions occurred on Hamming distance, alternating strings, and trace computation. Some selected-adapter outputs were executable but incorrect where base outputs had been invalid, moving observed errors from parsing into runtime behavior. Longer selected-adapter completions coincided with a 2,065.4-second external evaluation versus 1,116.5 seconds for base (1.85$\times$) and one additional timeout; the run did not isolate a causal timing mechanism \cite{hubresults}.

Accordingly, the evidence supports the narrow claim that verifiable GRPO completed, changed the adapter tensors, and coincided with fewer invalidly structured internal candidates in this comparison. It does not support a broad claim of improved software engineering. All three paired intervals---validation, internal final, and external---include zero.

\section{Experiment history and corrective loop}

An initial diagnostic run completed preflight, preparation, baseline, and a two-step smoke check, but its terminal displayed a Trackio conversion warning when TRL emitted undefined clip extrema for an entirely clipped batch. That stderr warning was not persisted in the structured log, and a later-inspected Trackio database was mutable and absent from the artifact manifest; the evidence therefore does not establish that Trackio durably dropped a complete record. The run was stopped manually before main training. The fix subclasses the official callback, removes only \texttt{None} fields, and retains zero and negative metrics. Curriculum review at the same boundary found two hidden suites that did not catch their authored bugs and one cross-split structural collision; all were corrected and re-audited before the completed run.

This diagnostic evidence is not pooled with the final experiment because its source, data, and manifest hashes differ. The completed loop was: define a small verifiable domain; state the gate; audit data and isolation; measure the base; prove gradient/save/reload viability; train 100 steps; decide the budget from training plus validation; lock; score each final benchmark once per compared system; export; publish; re-download; and report both positive and neutral outcomes.

\section{Threats to validity}

\textbf{Statistical power.} The internal sets contain only 12 tasks each and the experiment has one training seed. One solved task moves a pass rate by 8.33 percentage points. Bootstrap intervals quantify paired task uncertainty but not variation across training seeds or curriculum construction.

\textbf{Selection.} Validation is intentionally optimistic because it selects the checkpoint and budget. Only final-test and external results estimate post-selection behavior.

\textbf{Benchmark exposure.} No HumanEvalPack row, model outcome, or score entered training, reward computation, selection, hyperparameter changes, or the budget decision. This data-flow statement does not prove that benchmark concepts were unknown to the authors, and upstream base-model pretraining exposure cannot be ruled out. Both evaluated policies share the latter risk.

\textbf{Protocol comparability.} The external prompt uses the raw HumanEvalFixDocs instruct form rather than Qwen's chat template, and the 3-second deadline differs from the BigCode harness. The measured numbers must not be compared directly with stock leaderboard entries.

\textbf{Security.} Containers share the host kernel and are not perfect hostile-code virtual machines. The setup uses no host bind or named-volume mount and no Docker socket, but it does mount an isolated \texttt{/tmp} tmpfs. Higher-assurance deployments should add a disposable VM, rootless Docker, user namespaces, seccomp/AppArmor, or a microVM boundary.

\textbf{Scope.} Synthetic pure-function repair does not test repository navigation, dependency management, multi-file patches, tests written by the model, or long-horizon agent behavior.

\section{Reproducibility and artifacts}

The producing source commit is \texttt{\SourceCommit}. Public configuration, curriculum, and manifest SHA-256 hashes are retained with the experiment report \cite{sourcecommit,runsummary}. The project required Python 3.12 or newer, but the persisted run environment did not capture the Python patch release. It did record PyTorch 2.14.0+cu130, Transformers 5.16.1, TRL 1.12.0, PEFT 0.20.0, and Docker 29.4.1 on an NVIDIA GeForce RTX 5070 Laptop GPU. Full prompt/completion pairs, reward breakdowns, and per-step metrics were recorded in append-only logs; environment, checkpoint, selection, evaluation, export, and phase state were retained in separate artifacts rather than all being fields of one log.

The public Hugging Face repository is
\begin{center}
\url{https://huggingface.co/BurnyCoder/qwen2.5-coder-0.5b-swe-rl}
\end{center}
at immutable original result revision \texttt{\HubRevision}. Its root contains the merged model, tokenizer, card, configuration, and measured results; \texttt{adapter/} contains the separate LoRA \cite{hubresults}. The original publish phase re-downloaded that exact revision, loaded the root model, and produced a non-empty greedy repair, but did not compare weight hashes. An independent post-publication check later found byte-identical local and downloaded Safetensors: merged SHA-256 \texttt{e6b2d3884e72fe8322eaa5fe181ce530593f710b8b4efdcf2012b911d2416a70} and adapter SHA-256 \texttt{37f5f71fae87a4fcc5b3df40d325544271d28cf7b55d6a0262c6096d6233b1b2} \cite{verification}.

\section{Conclusion}

MiniBug-RL answers the engineering question affirmatively for the recorded system: a complete single-function software-repair RL loop, including verifiable rewards, low-rank updates, split discipline, resource-limited execution, paired evaluation, model export, and public reload verification, completed on an 8~GB GPU at \TrainPeakGiB{}~GiB measured peak allocated training memory. The scientific result is more restrained. The selected adapter solved one additional task on each selection-held-out benchmark and had substantially fewer malformed internal outputs, but average greedy correctness did not reliably improve and every paired interval includes zero. The appropriate next experiment is a larger structurally diverse training curriculum and multiple seeds, selected without tuning against the current model-scored final sets.
